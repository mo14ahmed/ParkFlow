Architecture overview

Swipe sideways to see the full diagram.

The system is organized into three layers: the parking buildings, the cloud, and the user-facing clients. In each building, space sensors (supported by computer vision) report whether each space is occupied or empty, an NFC reader handles stored-value cards, and a gate motor with a local LCD and LEDs controls entry and exit. These devices connect to a local gateway, such as a Raspberry Pi, that runs the gate logic on its own, keeps working if the internet drops, and buffers events to replay once the connection returns. The first building is real hardware, and the additional buildings are simulated to show that the design scales.

The gateway communicates with the cloud through an MQTT broker. MQTT is a lightweight publish/subscribe messaging protocol designed for constrained devices and unreliable networks (Banks & Gupta, 2014). Devices publish small messages to named topics, and any subscriber to a topic receives them through a central broker. A single backend server, split into clear modules, consumes those messages. The modules cover device communication, live occupancy, space assignment and routing, accounts and wallet billing, logging and analytics, and admin functions such as roles and manual gate override.

The backend stores users, cards, ledgers, sessions, events and buildings in a PostgreSQL database, and keeps the 3D models and floor maps in file storage. It exposes a REST API for actions (Fielding, 2000) and a WebSocket for live updates. The public website with its interactive 3D viewer, the iOS app with CarPlay support, and the admin dashboard all use that same API, so every client sees the same live data.

Development approach

We will use the Agile methodology to build the website and to manage the project (Beck et al., 2001). Work is split into short sprints, each delivering a small working piece, such as live availability, then the 3D viewer, then accounts and the wallet. A prioritized backlog is reviewed at the end of every sprint, so feedback and changing requirements can be handled early instead of at the end.

Cloud server

The cloud layer runs on a dedicated VPS. Each parking building's gateway connects to it to report occupancy and gate events, and the same server hosts the public website and the REST API used by the iOS and desktop applications. The website is available at www.parkflow.tech.

Camera

  • Defined a fixed, high-angle camera position so one camera covers multiple parking spots.
  • Candidate camera: Arducam 8MP IMX219 USB. It is compatible with Windows, Linux and Raspberry Pi, inexpensive, and easy to mount.

Space mapping and detection

  • Parking spaces are mapped in OpenCV, with each spot defined manually as a polygon.
  • The polygons work together with YOLO vehicle detection, which uses fast, real-time capable pretrained CNN models.
  • A vehicle detected inside a spot marks that polygon as occupied.

Tracking and state changes

  • ByteTrack (real-time performance) or DeepSORT (object tracking and identity) will change a spot's state between free and occupied only once a threshold of n consecutive frames is met.

Sensors

Proposed infrared break-beam sensors in a two-stage sequence at both lanes: entrance sensors (E1, E2) detect approach and passage, and exit sensors (X1, X2) confirm a vehicle leaving.

Difficulties encountered

Issues found during the period and how we plan to address them.

Group

Our main challenge as a group was finalizing the scope after adding new modules (computer vision, website, routing and digital twin), since each one affected the others' requirements. Choosing between many hardware and software options, such as camera types, detection models, display types and gate sensors, took more research time than expected, and agreeing on one common data format for the CV, backend, gate and digital twin required several rounds of discussion. We also revised the overall architecture from a peer-to-peer design to a centralized cloud server after identifying consistency, security and management problems.

To keep progress on track, we split the research by subsystem and will hold regular integration checkpoints in the next period so each subsystem stays aligned with the shared architecture.

Student AMohamed Abouzaid

In the first two weeks, I planned to design the system as a peer-to-peer (P2P) network, where each parking building (or even each parking space) would act as a peer and communicate directly with the others to share availability. As I worked through the design, I found that this approach creates several serious problems for a system like ours (Androutsellis-Theotokis & Spinellis, 2004; Lua et al., 2005):

  • Inconsistent data: without one source of truth, peers can hold conflicting views of the same space or the same card balance. Two buildings could assign the same space, or a stored-value card could be charged twice, because no node has the final say.
  • No single point for clients: the website, iOS app and desktop apps would need to locate and query many peers to build a complete picture, instead of calling one API.
  • Security and trust: payments, card authorization and admin overrides need a trusted authority. In a P2P network every peer must be trusted, and a compromised node can spread false data.
  • Peers going offline: when a building's node goes offline, its data becomes unavailable to the rest of the network unless it is replicated across peers, which adds complexity.
  • Growing connection count: in a fully connected network the number of links grows as n(n−1)/2, so every new building adds connections to all the others.
  • Hard to manage: software updates, logging and analytics would have to be handled across every node instead of in one place.

Solution: I changed the design to a centralized client-server architecture. Each building runs a local gateway that keeps the gate working offline and buffers events. All gateways report to one cloud server through an MQTT broker. The cloud server is the single source of truth for occupancy, accounts and billing, and serves one API to all clients.

Student CJulian Vila

The main design challenge is telling a vehicle that passes through the gate apart from one that approaches and reverses, stops in the sensor beam, or triggers the sensors more than once.

Possible solution: use the ordered E1 to E2 and X1 to X2 sensor sequences, require a valid state transition before counting a vehicle, and add a short re-trigger lockout or event confirmation to prevent duplicate counts.

A sensor obstruction or failure could leave the gate in an unsafe or indeterminate state.

Possible solution: add timeout and fault states. When passage is uncertain, keep the gate from closing onto the vehicle and require recovery or manual intervention.
